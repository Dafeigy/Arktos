# Arktos 开发计划

## 1. 目标

本计划面向 Arktos 的 0 到 1 实现，目标是在 Python 技术栈下交付一个可供企业内部应用接入的输入前检测服务，具备以下最小闭环能力：

- 统一检测 API
- 敏感信息检测
- Prompt Injection / Jailbreak 检测
- 内容审核基础能力
- 自定义规则策略
- 审计日志与基础可观测性

## 2. 建议技术方案

### 2.1 技术栈

- 语言：Python 3.11+
- Web 框架：FastAPI
- 数据校验：Pydantic
- 异步运行：Uvicorn / Gunicorn
- 缓存与配置热加载：Redis
- 数据库：PostgreSQL
- 搜索与分析：首期可直接用 PostgreSQL，后续可引入 Elasticsearch / OpenSearch
- 消息队列：Kafka 或 RabbitMQ（用于审计异步化，可后置）
- 监控：Prometheus + Grafana
- 日志：结构化 JSON Logging
- 部署：Docker + Kubernetes

### 2.2 架构建议

建议采用模块化单体起步，后续再按负载拆分服务。原因是规则、策略、审计和检测链路高度耦合，0 到 1 阶段先控制复杂度更重要。

建议模块：

- `api`：对外 HTTP 接口
- `orchestrator`：检测链路编排
- `detectors`：各类检测器插件
- `policy`：策略决策与规则管理
- `redaction`：脱敏处理
- `audit`：审计日志与事件记录
- `storage`：配置与数据访问层
- `metrics`：指标与 tracing

## 3. 核心能力拆解

### 3.1 检测链路编排

职责：

- 输入标准化
- 路由策略选择
- 并发执行检测器
- 聚合风险结果
- 输出动作决策

交付要求：

- 支持同步调用
- 支持检测器超时控制
- 支持单检测器失败降级

### 3.2 敏感信息检测器

首期实现：

- 正则规则库
- 词典检测
- 可配置白名单
- 命中片段脱敏

后续增强：

- 上下文识别
- 机器学习/LLM 辅助分类

### 3.3 Prompt Injection / Jailbreak 检测器

首期实现：

- 常见注入语句模板
- 越狱关键词和模式库
- 编码/分段绕过基础识别
- 风险评分机制

后续增强：

- 语义分类模型
- 对抗样本回归集

### 3.4 内容审核检测器

首期实现：

- 规则+词典分类
- 可扩展风险标签体系

后续增强：

- 接入内部或第三方审核模型

### 3.5 自定义规则引擎

建议规则模型支持：

- 规则元数据
- 表达式条件
- 作用范围
- 优先级
- 动作类型
- 生效版本

规则 DSL 可先简化为 JSON 配置，不必首期自建复杂脚本语言。

### 3.6 审计与反馈

建议记录：

- 请求摘要
- 命中规则
- 决策结果
- 脱敏前后哈希或安全摘要
- 策略版本
- 检测耗时
- 上游应用标识

反馈能力：

- 标记误报
- 标记漏报
- 样本回流到规则优化流程

## 5. 开发阶段规划

### Phase 0：方案确认与样本准备（1 周）

目标：

- 确认核心场景
- 定义风险分类
- 梳理输入数据样本
- 明确首期规则范围

产出：

- PRD 定稿
- 技术方案说明
- 初始测试样本集
- 风险分类字典

### Phase 1：MVP 核心服务（2-4 周）

目标：

- 建立可运行的检测 API
- 跑通规则检测与决策闭环

开发项：

- FastAPI 服务骨架
- 健康检查与基础中间件
- 检测请求/响应模型
- 编排器基础实现
- 敏感信息规则检测器 v1
- 注入/越狱检测器 v1
- 内容审核检测器 v1
- 策略决策引擎 v1
- 审计日志落库
- 基础单元测试

验收标准：

- 能对一段输入完成检测并返回决策
- 能记录命中规则和 trace ID
- 核心检测路径有测试覆盖

### Phase 2：策略中心与可运维能力（2-3 周）

目标：

- 提升配置能力和可运营性

开发项：

- 规则配置持久化
- Redis 缓存与热更新
- 多租户/多应用策略路由
- 白名单机制
- 指标埋点
- Prometheus 监控
- 错误码与告警体系

验收标准：

- 不重启服务即可更新规则
- 不同应用可使用不同策略
- 可查看关键指标与错误情况

### Phase 3：准确率优化与样本反馈（2-4 周）

目标：

- 提高召回率与降低误报

开发项：

- 误报/漏报反馈机制
- 回归样本测试集
- 风险评分与阈值优化
- 脱敏策略增强
- 检测结果解释信息增强

验收标准：

- 回归样本可自动跑批
- 核心规则调整可量化评估效果

### Phase 4：增强能力（持续迭代）

可选方向：

- 接入模型辅助检测
- 管理后台
- 异步事件流
- A/B 策略实验
- 输出侧 GuardRails

## 6. 团队分工建议

如果是小团队，建议最少配置：

- 1 名后端工程师：服务框架、API、存储
- 1 名安全/规则工程师：规则库、测试样本、策略设计
- 1 名平台或全栈工程师：管理能力、运维接入、可观测性

如果只有 1-2 人，也可以先按下面顺序推进：

1. API 和编排器
2. 敏感信息规则
3. 注入/越狱规则
4. 审计与测试样本
5. 配置中心

## 7. 数据与规则建设建议

首期最容易被低估的部分不是代码，而是样本和规则资产。建议尽早建立：

- 敏感信息正则库
- 企业私有词典
- Jailbreak 样本库
- Prompt Injection 模板集
- 合规分类标签体系
- 误报样本集
- 漏报样本集

建议规则以文件化配置管理，并纳入版本控制，方便审查和回滚。

## 8. 测试策略

### 8.1 单元测试

- 每个检测器独立测试
- 规则命中和白名单逻辑测试
- 决策引擎测试

### 8.2 集成测试

- API 请求链路测试
- 数据库存储测试
- 配置热更新测试

### 8.3 回归测试

- 使用固定样本集评估每次规则变更
- 输出准确率、误报率、漏报率变化

### 8.4 压测

- P50 / P95 / P99 延迟
- 并发场景下吞吐量
- 外部依赖故障时的退化行为

## 9. 风险控制建议

- 不要首期就过度依赖 LLM 作为唯一检测器，成本、稳定性和解释性都不理想。
- 不要一开始做复杂规则 DSL，先用结构化 JSON/YAML 即可。
- 不要忽略日志脱敏，否则审计系统本身会变成泄露面。
- 不要把所有业务都绑到一套全局规则上，策略隔离很关键。

## 10. 首期交付建议

为了尽快让 Arktos 具备接入价值，建议首个可交付版本包含：

- `POST /v1/inspect`
- `GET /health`
- 敏感信息规则检测
- Prompt Injection / Jailbreak 检测
- 基础内容审核
- 决策动作：`Passed`、`Masked`、`Blocked`
- 文件化规则配置
- 审计日志与基础监控

## 11. 下一步建议

文档完成后，可以立刻进入三个动作：

1. 先定义 `inspect` API 的请求响应 schema。
2. 再初始化 Python 项目骨架和模块目录。
3. 最后优先实现敏感信息与注入检测两类 MVP 检测器。

这样我们可以在最短时间内把“文档规划”推进成“可运行服务”。
