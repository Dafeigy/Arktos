# Arktos PRD

## 1. 文档信息

- 产品名称：Arktos
- 产品定位：面向企业内部 LLM 应用的输入前检测 GuardRails 服务
- 版本：v0.1
- 文档状态：初稿
- 目标读者：产品、平台工程、AI 应用开发、安全与合规团队

## 2. 背景与问题定义

随着企业内部越来越多的应用接入大语言模型，输入侧的安全与合规风险快速上升。大量问题并不发生在模型输出之后，而是在请求进入模型之前就已经埋下隐患，例如：

- 用户在提示词中粘贴了内部敏感数据、密钥、账号、代码片段或客户信息。
- 恶意用户通过 Prompt Injection、Jailbreak、角色伪装、越权指令等方式诱导模型突破既定边界。
- 业务应用缺少统一的内容审核能力，导致涉政、暴力、色情、歧视、自残、违法等高风险内容直接进入下游模型或业务流程。
- 不同业务团队各自实现零散的规则，造成标准不统一、维护成本高、审计能力弱。

企业需要一个位于 LLM 调用链前置环节的统一检测服务，在请求进入模型之前完成风险识别、策略决策、脱敏改写、阻断放行和审计留痕。

## 3. 产品愿景

Arktos 的目标是成为企业内部 AI 应用的标准输入风控层，为不同业务提供统一、可配置、可审计、可扩展的 GuardRails 能力。

一句话定义：

Arktos 是一个在用户输入进入 LLM 之前执行安全、合规和策略检查的 Python 服务。

## 4. 产品目标

### 4.1 核心目标

- 降低企业内部敏感信息泄露风险。
- 识别并拦截常见 Prompt Injection 与 Jailbreak 攻击。
- 为内容安全与合规提供统一的输入审核能力。
- 提供灵活的自定义规则与策略编排能力，适配多业务场景。
- 为安全运营和审计提供可追溯的检测记录与决策依据。

### 4.2 非目标

- 不负责替代企业 DLP 全量体系。
- 不负责模型输出侧的完整审核与治理。
- 不负责终端侧输入采集或浏览器插件能力。
- 不直接承担身份鉴权平台职责，可对接现有 IAM/API Gateway。

## 5. 目标用户

- 企业内部 AI 平台团队：需要统一接入层与治理能力。
- 业务应用开发团队：希望以低成本接入输入检测能力。
- 安全与合规团队：需要统一策略配置、事件审计与规则治理。
- 运维/SRE 团队：关注服务稳定性、性能、告警和可观测性。

## 6. 核心使用场景

### 场景 1：企业知识助手输入防泄露

员工向知识助手提问时，输入中包含内部代码、客户手机号、Access Token、数据库连接串等敏感信息。Arktos 在请求进入模型前检测并执行拦截、脱敏或告警。

### 场景 2：内部 Copilot 防注入与越狱

开发 Copilot 或运营 Copilot 在使用过程中遭遇恶意提示词，例如要求忽略系统指令、输出凭据、模拟管理员身份。Arktos 识别攻击模式并阻断请求。

### 场景 3：面向员工或客户的智能表单审核

用户在工单、聊天、总结、搜索等输入中提交违规或高风险内容。Arktos 根据合规策略做拦截、分级处理或人工复核标记。

### 场景 4：多业务线自定义策略治理

法务、HR、研发、客服等不同场景对输入内容的管控标准不同。Arktos 支持业务按租户、应用、场景、环境配置不同规则集和动作策略。

## 7. 产品范围

### 7.1 In Scope

- 文本输入检测
- 敏感信息识别与脱敏
- Prompt Injection / Jailbreak 检测
- 内容合规与有害内容审核
- 自定义规则引擎
- 策略编排与决策动作
- 检测结果解释与审计日志
- API / SDK 接入能力
- 管理端基础配置能力

### 7.2 Out of Scope（首期）

- 图片、音频、视频输入审核
- 完整工作流编排平台
- 高级对抗训练平台
- 全功能可视化低代码策略平台

## 8. 功能需求

### 8.1 输入检测 API

提供统一的服务接口，供上游应用在调用 LLM 之前发起检测请求。

输入建议包含：

- `app_id`
- `tenant_id`
- `environment`
- `user_id` 或匿名主体标识
- `session_id`
- `text`
- `context`：可选的历史消息、业务元数据、标签
- `policy_id` 或自动策略选择标识

输出建议包含：

- `decision`：Passed / Masked / Blocked
- `risk_level`：low / medium / high / critical
- `matched_rules`
- `detectors`
- `redacted_text`
- `reason_codes`
- `trace_id`
- `latency_ms`

### 8.2 敏感信息检测

首期支持以下类别：

- 凭据类：API Key、Token、AK/SK、JWT、Cookie、私钥片段
- 身份类：手机号、邮箱、身份证号、员工号、银行卡号
- 基础设施类：IP、域名、数据库连接串、内部路径、主机名
- 代码与配置类：配置文件片段、环境变量、密钥文件内容
- 企业自定义词典：项目代号、客户名单、部门黑词、内部资产标识

检测方式：

- 正则规则
- 词典匹配
- 上下文模式识别
- 可选的模型辅助分类

处置动作：

- 标记
- 局部脱敏
- 全量拦截
- 记录审计并放行

### 8.3 Prompt Injection / Jailbreak 检测

识别以下模式：

- 忽略、覆盖、绕过系统指令
- 身份冒充、权限提升、开发者模式伪装
- 提示分段混淆、编码混淆、翻译绕过
- 要求输出机密、内部提示、策略内容
- 社会工程式诱导或越权工具调用意图

检测方式：

- 规则模板
- 特征关键词与语义模式
- 组合评分策略
- 可插拔模型分类器

### 8.4 内容合规与有害内容审核

覆盖以下风险类型：

- 暴力与伤害
- 色情与低俗
- 仇恨与歧视
- 自残与自杀
- 违法犯罪
- 涉政敏感
- 骚扰与侮辱
- 业务自定义高风险内容

处理策略：

- 直接拦截
- 分级放行
- 仅告警
- 转人工复核标记

### 8.5 自定义规则与策略编排

管理员可按租户、应用、环境配置规则集，支持：

- 启用/禁用检测器
- 设置命中阈值
- 定义优先级
- 定义动作映射
- 按场景路由不同策略
- 支持灰度发布与回滚

规则建议支持如下能力：

- 精确匹配
- 正则匹配
- 关键词词典
- 逻辑组合：AND / OR / NOT
- 白名单/例外规则
- 命中次数阈值

### 8.6 审计与可观测性

支持查询：

- 请求总量、拦截量、脱敏量、误报反馈量
- 按租户/应用/规则/风险类型的统计
- 高频命中规则
- 风险趋势变化
- 检测链路耗时
- 决策明细与追踪 ID

### 8.7 管理控制台（首期可简化）

首期可先提供最小化管理能力：

- 策略配置
- 规则开关
- 命中记录查询
- 样本反馈标注

管理端首期可先采用内部管理 API + 简单页面，不要求一步到位做重型平台。

## 9. 非功能需求

### 9.1 性能

- 单次检测接口 P95 延迟目标：`< 150ms`（纯规则路径）
- 单次检测接口 P95 延迟目标：`< 400ms`（启用模型辅助检测）
- 支持水平扩展
- 支持高并发无状态部署

### 9.2 可用性

- 服务可用性目标：99.9%
- 关键路径具备超时控制、降级与熔断
- 外部模型检测器故障时可回退到规则模式

### 9.3 安全

- 检测日志敏感字段需脱敏存储
- 管理接口需鉴权与权限分级
- 配置变更需审计记录
- 支持租户隔离

### 9.4 可维护性

- 检测器插件化
- 规则热更新
- 配置版本化
- 单元测试与回归样本集

## 10. 核心决策流程

建议的处理链路：

1. 请求进入 Arktos。
2. 基础元数据校验与策略路由。
3. 执行预处理，例如文本标准化、编码解码、长度裁剪。
4. 并行执行敏感信息检测、注入/越狱检测、内容审核、自定义规则检测。
5. 聚合检测结果并计算风险分。
6. 根据策略输出 `Passed` / `Masked` / `Blocked`。
7. 记录审计日志与指标。
8. 将处理结果返回上游应用。

## 12. 风险与挑战

- Prompt Injection 和 Jailbreak 形态变化快，单纯依赖规则容易失效。
- 敏感信息检测容易在召回率与误报率之间失衡。
- 不同业务对“违规”的定义差异较大，需要策略层而非单一全局规则。
- 审计日志本身可能携带风险内容，需要二次脱敏与权限管控。
- 若模型辅助检测调用外部服务，需考虑数据边界与合规要求。

## 13. 里程碑建议

### M1：最小可用版本（4-6 周）

- 输入检测 API
- 正则/词典规则引擎
- 敏感信息检测首版
- Prompt Injection / Jailbreak 规则首版
- 内容审核基础分类
- 审计日志与基础指标

### M2：可运营版本（6-10 周）

- 策略中心
- 规则热更新
- 多租户/多应用配置
- 样本反馈与误报处理
- 风险报表

### M3：增强版本（10-16 周）

- 模型辅助检测器
- 更细粒度的脱敏策略
- 灰度发布与 A/B 策略实验
- 管理后台完善

## 14. MVP 建议

如果希望尽快落地，建议 MVP 只聚焦四件事：

- 做好统一检测 API
- 先把敏感信息和 Prompt Injection 两类核心风险打透
- 用规则引擎撑起 80% 场景
- 把审计、配置和样本沉淀能力做出来

原因是这四项已经足以支撑企业内部第一批应用接入，并且能尽早积累真实样本，为后续模型检测和精度优化提供数据基础。
